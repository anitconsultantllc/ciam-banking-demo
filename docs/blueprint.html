CIAM Banking Demo Blueprint

A small online-banking platform built to show CIAM, microservices, Java, Angular, React and C# working together. Review the architecture, layout and build plan here before any code is written. The cheat sheet at the end maps each part to the questions it prepares you for.

Decisions

What you've already confirmed, and what still needs an answer before scaffolding.

Confirmed

  • Full scope: 3 Java services, gateway, C# notification service, React and Angular portals.
  • Kafka is the event backbone between all services.
  • The C# Notification Service puts each outgoing message on RabbitMQ for durable delivery before sending it.
  • Repository on GitHub with CI.
  • Clean architecture in every backend service (see section 5).
  • No hard-coded config. Transfer limits, the step-up MFA threshold and email templates live in database tables. URLs and ports come from environment variables.

Open questions

  • Versions I originally said Java 21 + Spring Boot 3. The current LTS pairing is Java 25 + Spring Boot 4. I'd use it if every library we need supports it when I scaffold, and fall back to 21 + 3.5 otherwise. OK?
  • Repo Name ciam-banking-demo, public so interviewers can browse it?
  • Folder ~/Documents/ciam-banking-demo?
  • Tokens The SPAs hold tokens in memory (PKCE). The alternative is a BFF (backend-for-frontend), which is more "bank-grade" but adds a component. I recommend PKCE, with the BFF prepared as a talking point.

How the pieces work together

Three flows cover almost every interview question about this system. Walk the interviewer through them in this order.

Flow A · Sign in, then step up to MFA for a transfer

The customer signs in with just a password. When they try a transfer above the threshold, the Transfer Service rejects the token because it lacks the MFA level. The React app then sends them back to Keycloak for a TOTP code and retries with the same idempotency key.

  autonumber
  actor U as Customer
  participant R as React portal
  participant K as Keycloak
  participant G as API Gateway
  participant T as Transfer Service
  U->>R: Sign in
  R->>K: authorize with code_challenge (PKCE)
  K-->>R: authorization code
  R->>K: token request with code_verifier
  K-->>R: access token, acr = 1 (password only)
  U->>R: Send 500 to savings
  R->>G: POST /api/transfers + Idempotency-Key
  G->>T: forward (signature, issuer, expiry checked)
  T-->>R: 401 insufficient_user_authentication, needs acr 2
  R->>K: authorize again with acr_values = 2
  K-->>U: prompt for TOTP code
  K-->>R: new access token, acr = 2
  R->>G: POST /api/transfers, same Idempotency-Key
  G->>T: forward
  T-->>R: 202 Accepted, status PENDING

Flow B · The transfer saga and the notification pipeline

A transfer touches two accounts, but there is no distributed transaction. The Transfer Service orchestrates a saga: debit, then credit, and if the credit fails it refunds the debit. Every message a service publishes goes through its transactional outbox. The outbox row is written in the same database transaction as the state change, so a crash can never leave the database and Kafka out of sync.

sequenceDiagram

  Note over T: one DB transaction writes transfer PENDING + outbox row
  T->>KF: DebitAccount (transfer.commands)
  KF->>A: DebitAccount
  Note over A: skip if event id already processed, debit with version check
  A->>KF: AccountDebited (transfer.replies)
  KF->>T: AccountDebited
  T->>KF: CreditAccount
  KF->>A: CreditAccount
  alt credit succeeds
    A->>KF: AccountCredited
    KF->>T: AccountCredited
    T->>KF: TransferCompleted (transfer.events)
  else credit rejected, e.g. account closed
    A->>KF: CreditRejected
    KF->>T: CreditRejected
    T->>KF: RefundAccount (compensation)
    T->>KF: TransferFailed (transfer.events)
  end
  KF->>N: TransferCompleted or TransferFailed

  MQ->>N: sender takes job, sends SMTP, acks
  Note over N,MQ: 5 failed attempts with backoff, then the job moves to the dead-letter queue

The React app polls GET /api/transfers/{id} until the status is COMPLETED or FAILED. The UI shows "pending" in between, which is eventual consistency showing up in the UX.

Flow C · Staff locks a customer from the back-office

  1. A support_agent signs in to the Angular app. The route guard checks the role claim before the page loads.
  2. Angular calls POST /api/admin/customers/{id}/lock. The gateway routes it to the Customer Service, which re-checks the role with @PreAuthorize.
  3. The Customer Service disables the user through the Keycloak Admin API and revokes their sessions, so the customer is signed out everywhere.
  4. It writes an audit row (who, what, when, why) and publishes CustomerLocked through its outbox.
  5. The Notification Service emails the customer, and the Account Service freezes outgoing transfers.
Why both Kafka and RabbitMQ? Kafka is a durable, replayable log. Many services read the same event, each at its own pace, and ordering holds per key (we key by account ID). That makes it the right backbone. Sending email is a different job. Each message is independent, has to be delivered exactly once from our side, and needs its own retry timer. On a Kafka partition, one slow or failing email would block every message behind it. RabbitMQ acks each message separately, supports delayed retries and dead-letter queues, and a quorum queue keeps a job safe on disk until the SMTP send succeeds. So the notification service reads from Kafka and uses RabbitMQ as its outbound work queue.

Clean architecture

Yes, in every backend service.

Each Java service is a Maven multi-module project with four modules. It's the same shape as a .NET solution with Domain, Application, Infrastructure and Api projects, and the dependency rule is enforced the same way. A module can only import what its pom.xml declares, just as a .csproj can only use its project references. A wrong-direction import is therefore a compile error, not something a code review has to catch. An ArchUnit test (the Java version of NetArchTest) adds finer rules, such as "the domain may not import org.springframework".

Where it applies, and where it doesn't

  • Customer, Account, Transfer, Notification: full four-layer structure. The Notification Service uses the .NET layout you already know.
  • API Gateway: no layers. It's configuration plus two filters, and adding layers would only add ceremony. This is a good point to make in the interview: apply the pattern where there is business logic to protect.
  • React and Angular: the frontend version of the idea, feature folders (features/transfers) with core/ for auth and HTTP and shared/ for UI. Components never call fetch directly. They go through a feature's API service.
  • Mediator: we won't add a MediatR equivalent. Use cases are plain classes behind interfaces, which is how Java teams usually do it.

Build, run, deploy

Three loops: your inner dev loop, CI on every push, and the demo stack.

Inner loop on your machine

  1. docker compose --profile infra up -d starts Postgres, Keycloak, Kafka (KRaft mode, no ZooKeeper), RabbitMQ, Mailpit and Jaeger.
  2. ./mvnw install once, from the repo root. This is dotnet build for the whole solution, plus running tests and installing the modules into your local Maven cache.
  3. Run the service you're working on from IntelliJ with the debugger attached. Run the others from compose (--profile apps) or IntelliJ.
  4. npm run dev / ng serve for whichever frontend you're changing. Both hot-reload.

Containers

Each service has a multi-stage Dockerfile, the same pattern as a .NET sdk → aspnet build. For Java it's a JDK image that runs mvnw package, then a slim JRE image that runs the jar as a non-root user. The frontends build to static files served by nginx.

Java gotchas that catch .NET developers

  • @Transactional works through a proxy. Calling a transactional method from another method in the same class skips the transaction. By default it also rolls back only on unchecked exceptions.
  • Checked exceptions. The compiler makes you declare or catch them. Most modern Spring code uses unchecked (RuntimeException) ones.
  • No properties. Records give you amount() accessors. JPA entities use getters.
  • == on objects compares references. Use .equals(), and compareTo for BigDecimal, where 1.0 and 1.00 are not equals.
  • Lazy loading outside a transaction throws LazyInitializationException. We'll turn off open-in-view and map entities to domain objects inside the adapter.
  • Nullability. There's no string?. Use Optional for return values and validation annotations at the edges.

CIAM

How is CIAM different from workforce IAM?

CIAM serves customers at scale: millions of users who sign themselves up. It has to balance security with conversion, so it includes self-registration, social login, progressive profiling, consent and privacy regulations (GDPR, CCPA, GLBA for banks) and account-takeover defenses. Workforce IAM serves employees who are provisioned by HR (SCIM), with SSO into internal apps and device policies. Lost sign-ups aren't a concern there, but insider risk is.

In the demo: Keycloak realm with self-registration, Google login, consents page, brute-force lockout

CIAM

Explain OAuth 2.0 vs OpenID Connect vs SAML.

OAuth 2.0 is delegated authorization: an access token that lets a client call an API. OIDC adds authentication on top of it, with an ID token saying who the user is, plus discovery and userinfo endpoints. SAML is the older XML-based federation standard. It's still common for enterprise SSO and legacy banking platforms. New customer-facing apps use OIDC, and SAML appears when you federate with partners or older systems.

In the demo: both SPAs use OIDC. Keycloak can also broker a SAML identity provider if asked.

CIAM

Why Authorization Code + PKCE for a single-page app?

A browser app can't keep a client secret. The implicit flow put tokens in the URL and is deprecated. With PKCE, the app creates a random code_verifier and sends only its hash when the flow starts. To exchange the code for tokens it must show the original verifier, so a stolen authorization code is useless to an attacker.

In the demo: Flow A, steps 2–5

CIAM

Where should an SPA store tokens? Is that good enough for a bank?

In memory, never in localStorage, because any XSS could read it. Use short-lived access tokens (5 minutes) and refresh-token rotation. For a production bank I'd go further with the backend-for-frontend (BFF) pattern. A small server does the OAuth flow and keeps the tokens, and the browser only gets an httpOnly, SameSite session cookie, so tokens never reach JavaScript. It's the approach the current IETF browser-app guidance recommends for high-risk apps.

In the demo: in-memory tokens. The BFF is the "what I'd do in production" answer.

CIAM

How do you require MFA only for risky actions?

Step-up authentication. Keycloak assigns authentication levels (the acr claim): level 1 for password, level 2 for password + TOTP. The Transfer Service checks the claim against a configured threshold amount. If the level is too low, it returns 401 with error="insufficient_user_authentication" (RFC 9470). The client re-authenticates with acr_values=2 and retries. Low-friction sign-in, strong protection where the money moves.

In the demo: Flow A, steps 9–15. The threshold lives in transfer_config.

CIAM

How do microservices validate tokens?

Locally, using Keycloak's public keys (JWKS, cached): check the signature, iss, aud, exp, then roles and scopes. The gateway checks at the edge, and each service checks again, because a request reaching the service might not have come through the gateway (zero trust). Calling the introspection endpoint on every request adds latency and a single point of failure. That's why tokens are short-lived rather than revocable.

In the demo: dashed "JWKS keys" line in the architecture diagram, plus SecurityConfig in every service

CIAM

How do you defend against account takeover?

Use layers. MFA and step-up. Brute-force detection with lockout. Breached-password checks. Rate limiting per IP and per user at the gateway. Risk signals such as new device or impossible travel. Short sessions for sensitive actions. Notify the customer about security events (password change, new device, MFA removed) so they can react quickly.

In the demo: Keycloak brute-force settings, gateway rate limiter, notification emails for security events

CIAM

How would you migrate millions of users off a legacy login without forcing password resets?

Lazy migration. Keycloak's User Storage SPI checks credentials against the legacy system on a user's first login, then imports the user and re-hashes the password with the modern algorithm. Active users move over invisibly. After a cut-off date, the remaining dormant accounts go through a reset-by-email flow. Run both systems in parallel, measure migration percentage, and roll back per segment if needed.

In the demo: discussion only. It pairs well with the Corillian modernization story.

CIAM

How do you handle consent and the right to be forgotten across services?

Record each consent with its purpose, policy version and timestamp, and make it withdrawable. For erasure, publish a CustomerErased event. Every service that holds personal data must act on it, deleting or anonymizing and keeping only what regulation requires (banks must keep transaction records). Include erasure in each service's contract tests so a new service can't forget it.

In the demo: consents page in React, consent table in the Customer Service

Microservices

How do you decide service boundaries?

Use DDD bounded contexts: a service owns one business capability and its data. Align services with teams (Conway's law), so each team can deploy without coordinating. If two services always change together, they're really one service. I'd start with a modular monolith when the domain is unclear. Microservices pay off when teams and scaling needs are really independent.

In the demo: Customer, Account and Transfer are three separate contexts, each with its own database

Microservices

How do you keep data consistent without distributed transactions?

With a saga: a series of local transactions, each with a compensating action. With orchestration, one service drives the steps, which is easy to follow and debug. With choreography, services react to each other's events, which gives looser coupling but makes the overall flow harder to see. I used orchestration for transfers because money flows need a clear owner and an auditable state machine.

In the demo: Flow B, including the refund compensation

Microservices

What is the dual-write problem?

A service that writes to its database and then publishes to Kafka can crash in between. The two then disagree forever. The transactional outbox fixes it: write the event to an outbox table in the same database transaction, and a relay publishes it afterward. That gives at-least-once delivery, so consumers must be idempotent.

In the demo: libs/java-platform outbox relay, used by all three Java services

Microservices

How do you avoid charging someone twice?

Idempotency at two levels. The API takes an Idempotency-Key header, and a retried POST returns the original result. Each consumer records processed event IDs in the same transaction as its state change and skips duplicates. Optimistic locking (@Version) on the balance stops two concurrent debits from both succeeding.

In the demo: Flow A step 13 reuses the key. Account Service keeps a processed_events table.

Microservices

Why use Kafka and RabbitMQ together?

They solve different problems. Kafka is a replayable log with many independent consumer groups and ordering per key, which makes it the event backbone. RabbitMQ is a task queue with per-message acks, delayed retries and dead-letter queues. Email delivery needs independent retries, and a slow email must not block others in a Kafka partition. So the notification service reads Kafka and puts each email job on a durable quorum queue.

In the demo: bottom row of the architecture diagram. Recorded as ADR 0002.

Microservices

How do you stop one failing service from taking down the rest?

Prefer asynchronous messaging, so a service that's down just builds a backlog. Where calls are synchronous, give each one a timeout, retries with exponential backoff and jitter (idempotent calls only), a circuit breaker, and a bulkhead to cap concurrent calls. Rate-limit at the gateway. Degrade gracefully by showing cached or "pending" state instead of an error.

In the demo: Resilience4j on the Customer → Keycloak Admin API call. Stop the Account Service during a transfer and it completes after restart.

Microservices

How do you debug a request that crosses five services?

Distributed tracing. OpenTelemetry propagates a trace ID through HTTP headers and Kafka message headers, and every log line includes it. In Jaeger you see the whole transfer as one trace with timings per hop. Add RED metrics (rate, errors, duration) per service and alert on SLOs rather than on CPU.

In the demo: open Jaeger at :16686 and show one transfer spanning gateway → Transfer → Kafka → Account → Notification

Microservices

How do you evolve event contracts without breaking consumers?

Make only additive changes. Consumers act as tolerant readers and ignore unknown fields. Put a version in the event envelope. For breaking changes, publish a new event type alongside the old one and retire the old one once consumers have moved. A schema registry or checked-in JSON Schemas with contract tests catch mistakes in CI.

In the demo: contracts/events/*.schema.json, validated by both the Java and C# tests

Microservices

What's your testing strategy for microservices?

Mostly fast unit tests on the domain, which has no framework dependencies. Integration tests per service with Testcontainers use real Postgres and Kafka, not mocks. Contract tests on events and APIs check that services agree. A handful of end-to-end tests cover the critical journeys. Architecture tests keep the layers honest.

In the demo: every layer of the pyramid runs in CI

Which modern Java features do you use?

Records for value objects and DTOs. Sealed interfaces with pattern-matching switch, so the compiler checks that every event type is handled. Virtual threads, so ordinary blocking code scales like async code. Text blocks for SQL. var for local variables.

Java

What are the pitfalls of @Transactional?

It's proxy-based. Self-invocation within the same class bypasses it, and it only applies to public methods called from outside the class. By default it rolls back only on unchecked exceptions. Keep transactions short, and never make a network call (Kafka, HTTP) inside one. That's exactly why the outbox exists.

In the demo: transactions sit on the application service methods. Publishing goes through the outbox.

How do you avoid N+1 queries in JPA?

Use fetch joins or @EntityGraph for known access patterns, and DTO projections for read screens. Disable open-in-view so lazy loading can't hide in the web layer. Turn on SQL logging or Hibernate statistics in tests to catch regressions.

How do you handle money and concurrent balance updates?

Use BigDecimal with an explicit currency and rounding mode, never double. Wrap it in a Money value object so the rules live in one place. For concurrency, use optimistic locking with @Version and retry on conflict. Use pessimistic SELECT … FOR UPDATE only when contention is high.

Java

How do you secure a Spring Boot API with Keycloak?

Add the OAuth2 resource-server starter and set issuer-uri, and Spring fetches the JWKS and validates tokens. Add a JwtAuthenticationConverter that maps Keycloak's realm_access.roles to authorities. Then use @PreAuthorize on use-case entry points. The API should be stateless: no sessions and no CSRF tokens, because it uses bearer tokens.

Java

How do you run the JVM well in containers?

Recent JVMs read container memory limits. Size the heap with -XX:MaxRAMPercentage rather than fixed -Xmx. G1 is the right default collector, and ZGC suits low-latency needs. Run as a non-root user on a slim JRE image. For faster startup there's class-data sharing, or GraalVM native images for scale-to-zero.

Angular + React

When would you choose Angular over React?

Angular is a complete, opinionated framework: DI, router, forms, HTTP and testing are built in, and every Angular codebase looks alike. That suits large enterprise teams and forms-heavy internal apps. React is a UI library where you choose the router, data fetching and state tools. It's more flexible, has a huge ecosystem, and suits customer-facing products that iterate quickly. That's why the demo uses Angular for staff and React for customers.

In the demo: both frontends against the same APIs and the same Keycloak realm

Angular + React

How does change detection differ?

React re-renders a component when its state or props change and reconciles against the virtual DOM. You optimize with memo, stable callbacks, and by keeping state local. Modern Angular uses signals: fine-grained reactive values that update exactly the bindings that depend on them, without zone.js. Older Angular relied on zone.js to trigger checks and OnPush to limit them.

In the demo: Angular back-office uses signals throughout

Angular + React

How do you implement auth in each framework?

In Angular, an OIDC client library, an HttpInterceptor that attaches the token, and functional route guards (CanActivateFn) that check roles. In React, an auth context provider, a protected-route component, and a fetch wrapper that attaches the token and handles the step-up 401. In both, the UI hides what a user can't do, but the API is what actually enforces it.

In the demo: core/auth folder in each frontend

Angular + React

How do you manage state?

Separate server state from UI state. In React, TanStack Query handles server state (caching, retries, polling), and useState/context handles the rest. In Angular, services exposing signals, plus resource() or RxJS for async. I add a global store (Redux/NgRx) only when many distant components share complex client state, which is rarer than people think.

Angular + React

What frontend security concerns matter for banking?

XSS above all. Rely on framework escaping, and never use innerHTML or dangerouslySetInnerHTML with user data. Set a strict Content-Security-Policy. Keep tokens out of storage. Use CSRF protection if you switch to cookies (BFF). Audit dependencies and pin versions. Don't log personal data to the console or to analytics.

Full stack

How do you design REST APIs?

Resource-oriented URLs. Correct status codes, including 202 Accepted with a status URL for asynchronous work. Errors as application/problem+json (RFC 9457). Cursor pagination. Idempotency keys on unsafe operations. Versioning in the URL. An OpenAPI spec generated from code and published.

In the demo: Swagger UI on each service. Shared problem+json handler.

Full stack

How would this scale to millions of customers?

Services are stateless, so they scale horizontally behind the gateway. Kafka partitions keyed by account ID keep ordering per account while spreading load. Postgres gets read replicas and, eventually, partitioning. Keycloak runs clustered with a distributed cache. Static frontends go on a CDN. Watch the actual bottleneck, usually the database, before adding complexity.

To show that the contract between services is the event schema, not the language. Teams can use the best tool for them as long as they honor the contracts. C# + Corillian

What do you know about Corillian, and how would you modernize it?

Corillian built online-banking software (the Voyager platform) and was acquired by Fiserv in 2007. You're likely to meet it as a legacy platform to integrate with or move off. If you've worked with it, lead with that. For modernization, use the strangler-fig pattern: put a gateway in front, move identity to CIAM first with lazy migration, then carve out capabilities one at a time (notifications, then transfers). Sync data with change-data capture while both systems run, and switch traffic per customer segment.
